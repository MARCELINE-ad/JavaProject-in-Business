# DECISIONS.md

## Вариант

Номер варианта: 9.

Часть А: метод `parseHours` принимает значения с ведущими нулями. Регулярное выражение изменено на `^0*[0-9]+$`, поэтому `08` преобразуется в число 8. Проверка диапазона `[0, 16]` остаётся обязательной.

Часть Б: добавлен метод `addFormattedTimesheet(int[] hours)`, который возвращает строку вида `Пн:8, Вт:9, Ср:10, Чт:8, Пт:8`.

## Решение 1

Формулировка: разрешить ведущие нули только на этапе разбора входной строки, не изменяя внутреннее представление данных.

Альтернатива: сохранять исходные строковые значения вместе с массивом чисел. Такой подход усложняет интерфейс класса и создаёт два представления одного табеля.

Обоснование: после успешной проверки программа работает с `int[]`, поэтому `08` и `8` имеют одинаковое числовое значение. Изменение локализовано в `parseHours`, а методы расчётов сохраняют исходные контракты.

## Решение 2

Формулировка: формировать человекочитаемый табель с помощью цикла и `StringBuilder`.

Альтернатива: соединять пять отдельных строк оператором `+`. Это допустимо для фиксированного числа дней, но приводит к повторению и хуже показывает общий алгоритм.

Обоснование: массив сокращений дней задаёт соответствие индекса названию дня. Цикл добавляет разделитель только между элементами, поэтому строка не содержит лишней запятой в конце. Метод не выполняет ввод-вывод и остаётся частью бизнес-логики.

## Ответы на вопросы методички

### Вопрос 1

Наиболее важна проверка структуры в методе `parseHours` класса `TimesheetAnalyzer`: после `split(";", -1)` массив должен содержать ровно пять элементов. Ошибка в числе значений вероятна из-за пропущенного часа, двойного разделителя или лишней точки с запятой в конце. Сохранение пустых элементов с помощью аргумента `-1` позволяет обнаружить завершающий разделитель, а не потерять его при разбиении. Проверка расположена на границе системы, до преобразования значений и расчётов, поэтому некорректный ввод прекращает обработку по стратегии fail-fast и не вызывает обращений к отсутствующим элементам.

### Вопрос 2

Ключевые бизнес-правила сосредоточены в классе `TimesheetAnalyzer`, а правило варианта 9 реализовано в методе `parseHours`. Этот метод определяет допустимый формат входных данных: значение должно состоять из цифр, может иметь ведущие нули и после преобразования должно находиться в диапазоне от 0 до 16. Размещение правила здесь оправдано тем, что `parseHours` является единственной точкой валидации строкового ввода. Остальные методы получают уже проверенный массив и отвечают только за расчёты. Такое разделение не допускает дублирования проверки и позволяет менять формат ввода, не переписывая методы суммы, среднего и переработки.

### Вопрос 3

Блок Activity-диаграммы «Для каждого элемента: проверить `^0*[0-9]+$` и диапазон `[0, 16]`, преобразовать в `int`» соответствует циклу в методе `parseHours`. На каждой итерации программа сначала проверяет строковый элемент регулярным выражением, затем преобразует его через `Integer.parseInt` и контролирует диапазон. Если проверка не пройдена, поток переходит к формированию сообщения об ошибке; если все пять значений корректны, обработка продолжается вычислением показателей. Диаграмма показывает один логический шаг обработки массива, не повторяя каждый оператор Java отдельным блоком.

### Вопрос 4

Минимальное локальное изменение - смена порога дневной переработки с 8 до 9 часов. Для этого достаточно изменить значение константы `DAILY_NORMAL_HOURS` в одном классе `TimesheetAnalyzer`; структура программы и сигнатуры методов останутся прежними. Проверки `overtimeDays` потребуется обновить как спецификацию ожидаемого поведения, но бизнес-логика не должна распространяться по другим классам. Такая локализация достигнута тем, что `SelfCheck` только вызывает методы и сравнивает результат, а все правила расчёта находятся в одном специализированном классе.

## Фрагмент кода для анализа

В условии `i <= hours.length` допущена ошибка off-by-one: последняя итерация обращается к `hours[hours.length]`, хотя последний допустимый индекс равен `hours.length - 1`. Это приводит к `ArrayIndexOutOfBoundsException`. Правильное условие - `i < hours.length`. При соблюдении R1 массив содержит ровно пять значений, а исправленный цикл безопасно обрабатывает индексы от 0 до 4 без падения.
